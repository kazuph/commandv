LLM Orchestration Analysis Workflow ID: lifetime-classify.workflow.js ↗

Claudeを極限まで使い倒す、
Bunの「ライフタイム自動分類」の凄み

JavaScript超高速ランタイム「Bun」のリポジトリで、ZigのコードをRustに移植・連携する道標として走っているAIパイプライン。 単なるコード自動生成ではなく、「精密な静的解析」「ゲーム理論的多数決による自己デバッグ」をClaudeで行う革新的なワークフローを解剖します。

超難解な「翻訳」の自動化

Zigのポインタ（*T / ?*T）が、Rustにおける「誰に所有され、いつ消えるか」をコードの文脈（初期化と破棄）から見極め、11つの所有権モデルに落とし込みます。

3エージェント対話型検証

不確実な判定やサンプルに対して、「3体の自律エージェントを敵対的に競わせ、2票以上の異議（Refute）で判定を却下・上書きする」という強固な多数決フィルターを採用。

完全自律データシンセシス

分類・検証されたデータは即座に集計され、リポジトリにコミット可能な LIFETIMES.tsv（タブ区切りテキスト）形式として最終出力。人間はマージするだけで完了します。

■ ワークフローの3フェーズ構造

Phase 01: Classify
1エージェント / 1ファイル

生存期間の判定

Zigの各ファイルにつき1体のClaudeエージェントを割り当て、構造体のメンバ変数をスキャン。 init()やdeinit()、メモリ割り当て（allocator）の処理を追いかけ、Rustのどの型に該当するかをマッピング。

// AIのミッション
- 全ポインタフィールドを抽出
- 初期化/破棄の証拠（Evidence）を収集
- 一時判定クラスを設定
Phase 02: Verify
3人寄れば、反証アリ

敵対的相互監査 (3-Vote Refute)

判定難易度の高い「UNKNOWN」や自信度「low」のフィールド、および自信度「high」の12%をランダムサンプリング。 3体の監査エージェントが独立してレビュー。2票以上「Refute（反証）」が出れば元の判定は却下され、正しいクラスへ修正されます。

// エージェント同士の戦い
Agent A: "これはOWNEDで合ってる？"
Agent B, C: "いや、deinitで解放されてない。PARAMだ！"
→ 反証成功（判定の上書き適用）
Phase 03: Synthesize
統計＆TSV生成

コンパイル可能成果物への出力

全ての分類データがマージされ、各フィールドの生存期間クラスごとの集計統計を出力。 さらに、すぐにRustポートに使えるタブ区切りの LIFETIMES.tsv テキストを生成します。

// 成果物プレビュー
file.zig \t Struct \t Field \t class \t rust_type...
→ 移植作業用メタデータの構築完了！

                ■ 高精度分類を支える11つの所有権タクソノミー
            

            

                単に「スマートポインタに置換する」のではなく、Rustコンパイラに最適で安全な型を選択するため、Claudeにインプットされる分類の定義は恐ろしく精緻化されています。
            


            

                
            

        


        
        

            

                

                    
                    このワークフローの「凄み」と設計思想
                

                
    
                    
  • 
                        1.
                        
    
                            コード自動化ではなく、人間の移植・再設計の支援
                            コード全体をいきなりAIにRustに書き直させるのではなく、「ポインタをどう管理すべきか」というアーキテクチャ設計メタデータ（TSV）に変換し、人間が自信を持って判断できるようにしている点。
                        
    
                    
    • 
                    
  • 
                        2.
                        
    
                            アドバーサリアル（敵対的）相互検証
                            AIは1度正しいと思い込むとハルシネーション（誤判定）を維持しやすい。このワークフローは、別エージェントに「Claimed Class」と「Evidence」を渡し、「間違っているはずだ。反証せよ！」という敵対的ポジション（Adversarial）から監査させることで、信じられないほどの高い精度を実現しています。
                        
    
                    
    • 
                    
  • 
                        3.
                        
    
                            ランダムサンプリング監査によるコスト効率化
                            全ファイルを3-voteで回すと莫大なAPIコストがかかります。そこで、自信度が「low/UNKNOWN」のものだけ全監査し、自信度「high」のものは12%だけを抜き出して監査し、予算と精度の最適なバランスをとっています。

                        実務から読み取れる背景
                    

                    

                        Bunは超高速なJavaScript実行環境であり、内部はZigで記述されています。一方、JavaScriptエンジンであるSafariのJavaScriptCore（JSC）はC++で書かれています。
                        そして最近のBunは徐々にRustを採用し始めています（例: bun_sys や新HTTPスタック）。
                    

                    

                        メモリ安全性をZigのようにマニュアル管理する言語から、コンパイラが厳密な生存期間（Lifetimes）を強要するRustへ移行・相互運用する場合、この「ポインタの所有権はどこにあるか？」の解明が最も手間で、最も壊れやすい壁になります。
                        このスクリプトはまさに、そのBun開発陣が直面する最大の苦行を突破するために生まれた、極めて実戦的な知恵の結晶なのです。
                    

                

                
                

                    

                        
                    

                    

                        気づき
                        「AIにプログラミングさせる」とは、コードの単純置換だけではなく、こうして専門的な概念のメタモデル（タクソノミー）を教え込み、高度な分類と監査のプロセスを自律化させることだと教えてくれます。
